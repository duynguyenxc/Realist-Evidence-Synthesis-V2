# Full-text acquisition: what was obtainable, and why the rest was not

Generated by `scripts/acquisition_report.py` from `studies_metadata.jsonl` and the contents of `fulltext/`. No model was called; this cost nothing but time and bandwidth.

## The flow, with the distinction that was being lost

| | Records | Share of pool |
|---|---|---|
| Candidate records in the pool | 1863 | 100% |
| Catalogue publishes an open-access PDF location | 1266 | 68% |
| **PDF actually downloaded and verified as a PDF** | **572** | **31%** |
| Open-access link that could not be fetched | 694 | 37% |

572 files on disk, 474 MB. Every one begins with the `%PDF` magic bytes; nothing HTML was saved as a PDF.

**The number to quote is 572, not 1266.** Earlier reports said "68% with a free full text", which was the share with an open-access *link*. The share we hold is 45% of those links.

## Why the rest failed

Diagnosed rather than assumed: one failed URL per publisher host, requested twice, once with the pipeline's own User-Agent and once with a browser's.

| Host | Pipeline UA vs browser UA | Reading |
|---|---|---|
| `doi.org` | 403 both | DOI resolver, not a direct PDF location |
| `www.mdpi.com` | 403 both | CDN bot block |
| `www.tandfonline.com` | 403 both | CDN bot block |
| `www.frontiersin.org` | PDF both | first-pass failure was transient |
| `onlinelibrary.wiley.com` | 403 both | CDN bot block |
| `pmc.ncbi.nlm.nih.gov` | 403 both | CDN bot block |
| `link.springer.com` | 200, not a PDF | landing page; the %PDF guard refused it |

**The User-Agent is not the cause.** Every host that refused the pipeline refused the browser string identically, so the pipeline is not being penalised for identifying itself honestly — and there is therefore no case for making it impersonate a browser, which would mean circumventing a publisher's stated bot policy to raise a count in a methods paper.

The largest single group is `doi.org`: the catalogue gave a DOI resolver where a direct PDF location was expected. Resolving it lands on a publisher page, not a file, so these are not retrievable by this route at all. Unpaywall publishes the direct location for exactly this case and would be the fix; its API requires a contact email address in every request, which is a decision for the RA rather than a default this script should set.

## Having the file is not the same as being able to read it

A PDF on disk is not yet evidence. It has to carry a text layer the pipeline can extract, and a corpus pulled off the open web does not uniformly do so. The figures below come from the ingest into the review database, not from the files:

| | Studies |
|---|---|
| Ingested into the review database | 572 |
| **With a usable full text** (20,000+ characters) | **539** |
| Partial text (1-19,999 characters) | 32 |
| No extractable text at all | 1 |

Mean length where any text was recovered: 56,050 characters.

**The number that governs extraction is the full-text one, not the file count.** Extraction reads the document; a study with no text layer contributes nothing to it however many megabytes it occupies.

## What this constrains

**For this review.** Screening works from titles and abstracts, which the pool has for 89% of records, so the 572 full texts do not limit screening. They limit **extraction**, which needs the full text of every included study. Whatever the screening decides, the included set has to be checked against what we can actually read, and anything we cannot will need requesting through the library.

**For the manuscript.** The reproducibility claim needs qualifying twice: OpenAlex ceased to be free and keyless on 2026-02-13, and roughly two thirds of nominally open-access full texts cannot be fetched by an unattended process. A reader with our protocol, our queries and no institutional access does not arrive at our corpus. Both belong in the limitations, not a footnote.

**For the pipeline.** The retry is now built in. The first pass obtained 434 files and a second identical run obtained 135 more, so a quarter of the corpus had been arriving by an accident of operator habit; `acquire_fulltext` now retries timeouts, connection errors, 429 and 5xx with backoff, and deliberately does not retry a 403 or a landing page. **One improvement is still unmade**: an Unpaywall lookup would turn a DOI resolver into a direct PDF location, which is the largest single failure group. Its API requires a contact email in every request, which is the RA's personal data and the RA's decision. Neither is a model call.
